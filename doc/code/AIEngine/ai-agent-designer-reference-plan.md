# AI 智能体设计器参考吸收计划

## 1. 背景

当前项目已经具备 AI 平台基础能力：

- `AiPrompt`：提示词配置。
- `AiSensitiveWord`：输入/输出敏感词配置。
- `AiAgent`：智能体运行配置，对话端通过 `agentCode` 选择。
- `AiWorkflow`：工作流节点图，支持 `start`、`prompt`、`knowledge`、`llm`、`tool`、`condition`、`output`。
- `AIRegistry`：运行时工具注册中心。
- `Document`：知识库切片与向量检索数据。
- `AiConversation`、`AiMessage`：会话和消息记录。
- `AiWorkflowRun`、`AiWorkflowRunStep`：工作流运行日志。

但当前配置体验偏工程化：提示词、工具、工作流、智能体分别维护，配置人员需要理解多个页面之间的关系。参考系统的优势在于把这些能力收束为一个“智能体设计器”，按步骤引导用户完成智能体创建。

## 2. 当前主要问题

### 2.1 智能体和工作流职责边界不够清楚

当前智能体可以绑定 `workflowCode`，同时还要配置 `toolCodes`。而工作流节点中也会配置 `knowledge` 或 `tool` 节点。

这会出现一个配置矛盾：

```text
工作流 A 使用工具 1、2、4
智能体只勾选工具 1、2
保存智能体时可以成功
运行到工具 4 时才报“智能体未授权工具：4”
```

这说明当前系统允许出现“配置保存成功，但运行时失败”的智能体。

### 2.2 智能体不像一个完整产品

当前智能体主要是运行参数集合，缺少对话端需要的展示信息：

- 头像。
- 欢迎语。
- 默认推荐问题。
- 标签。
- 面向用户的能力说明。

这些字段不影响模型调用，但影响用户是否知道这个智能体能做什么、应该怎么问。

### 2.3 调试链路分散

当前已经有智能体测试弹窗和工作流运行记录，但配置、测试、运行日志之间没有形成完整闭环。用户配置完智能体后，无法在一个视图里清楚看到：

- 当前命中的智能体。
- 使用的提示词。
- 绑定的工作流。
- 工作流实际执行节点。
- 调用的工具和工具返回。
- 最终回答和错误原因。

## 3. 参考系统值得借鉴的点

参考系统把智能体设计拆成五步：

```text
基本信息 -> 模型与提示词 -> 工具与能力 -> 知识库与 MCP -> 高级设置
```

其中最值得当前项目借鉴的是：

### 3.1 分步骤智能体配置

把一个大表单拆成更接近业务心智的配置步骤：

1. 基本信息：名称、编码、头像、描述、欢迎语、推荐问题。
2. 模型与提示词：模型、模型参数、提示词。
3. 能力配置：工作流、工具依赖、工具策略。
4. 知识库：智能体可使用的知识范围。
5. 高级设置：历史消息数、运行日志展示、调试开关。

### 3.2 对话端展示配置

智能体应该能配置对话首页展示内容：

- 欢迎语用于空会话首屏。
- 推荐问题用于引导用户提问。
- 头像用于区分不同智能体。
- 描述用于说明能力边界。

### 3.3 工作流依赖自动分析

用户选择工作流后，系统自动解析工作流节点，提取依赖：

- `prompt` 节点依赖的 `promptId`。
- `knowledge` 节点依赖 `search_knowledge` 工具能力。
- `tool` 节点依赖对应 `toolCode`。
- `llm` 节点依赖模型调用能力。

前端展示依赖结果，后端保存时校验依赖满足情况。

### 3.4 轻量运行可观测

在智能体测试中展示一次请求的完整链路：

```text
用户问题
-> agentCode
-> promptId
-> workflowCode
-> workflow_start
-> node_start / node_end
-> tool 调用
-> sources
-> workflow_done
-> 最终回答
```

这比只展示最终回答更适合排查配置问题。

## 4. 不建议近期借鉴的点

以下能力有价值，但当前阶段不建议纳入近期范围：

- MCP 服务。
- 子智能体。
- Hook 钩子体系。
- 复杂长期记忆。
- Token 自动压缩策略。
- Studio 执行环境。
- 技能包运行时机制。

原因是这些能力会显著增加运行时优先级和配置组合复杂度。当前应先解决智能体、工作流、工具、知识库之间的基础职责边界。

## 5. 目标设计

### 5.1 核心定位

建议将当前 AI 平台收敛为以下关系：

```text
工具：底层原子能力，由 AIRegistry 注册。
提示词：可复用的系统提示配置。
工作流：流程编排，声明运行步骤和依赖能力。
智能体：对外发布入口，选择工作流并配置展示信息、模型参数、运行控制。
知识库：可被普通 RAG 或工作流 knowledge 节点使用的数据源。
```

### 5.2 智能体与工作流关系

智能体可以绑定工作流，但不应让用户重复猜测工作流需要哪些工具。

建议规则：

1. 如果智能体绑定了工作流，前端自动展示该工作流依赖的工具。
2. 后端保存智能体时校验工作流工具依赖。
3. `toolCodes` 可以保留为授权字段，但默认由工作流依赖自动填充。
4. 允许人工收窄额外工具授权，但不允许去掉工作流必需工具。
5. 如果提交的 `toolCodes` 不满足工作流必需工具，保存失败。

### 5.3 技能包定位

恢复技能包配置和安装入口。

当前阶段技能包作为提示词、工具、知识范围、工作流和智能体默认参数的能力集合：

```text
选择技能包
-> 自动填充提示词、工作流、工具、知识范围、推荐问题、模型参数
-> 保存后运行时只读取 AiAgent，不读取技能包
```

这样既保留技能的复用价值，又避免技能包成为独立于 AiAgent 的第四套运行入口。

## 6. 分期计划

### Phase 1：智能体配置体验整理

目标：让智能体像一个完整可发布对象。

当前状态：已完成后端和后台。小程序端按本次约定暂不处理。

改动范围：

- 后端 `AiAgent` 增加展示字段：
  - `avatar`
  - `welcomeMessage`
  - `recommendedQuestions`
  - `tags`
- 后台智能体页面改为分步骤表单。
- 聊天页空会话展示智能体欢迎语和推荐问题。
- 文档同步字段说明。

验收标准：

- 新增/编辑智能体可以维护欢迎语和推荐问题。
- 选择智能体进入聊天页后，空会话展示对应欢迎语。
- 点击推荐问题可以直接填入或发送。
- 不影响未配置欢迎语的旧智能体。

### Phase 2：工作流依赖分析和保存校验

目标：解决“工作流需要工具，但智能体未授权工具”的运行时失败问题。

当前状态：已完成后端和后台。小程序端按本次约定暂不处理。

落地范围：

- 后端已在智能体新增/编辑时校验工作流必需工具。
- 后端 `config-options` 已返回工作流 `requiredToolCodes` 和 `promptIds`。
- 后台智能体页已在选择工作流后自动合并并锁定必需工具。
- 小程序端暂不纳入本阶段。

改动范围：

- 后端增加工作流依赖提取逻辑：
  - 提取 `knowledge` 节点的 `search_knowledge`。
  - 提取 `tool` 节点的 `toolCode`。
  - 提取 `prompt` 节点的 `promptId`。
- `GET /ai-platform/agent/config-options` 或新增接口返回工作流依赖信息。
- 新增/编辑智能体绑定 `workflowCode` 时，校验必需工具是否被授权。
- 前端选择工作流后展示依赖工具和依赖提示词。

验收标准：

- 工作流使用工具 1、2、4 时，智能体只授权 1、2 会保存失败。
- 错误提示明确列出缺失工具。
- 工作流依赖工具全部满足时保存成功。
- 工作流无工具节点时不强制选择工具。

### Phase 3：智能体测试链路增强

目标：让配置人员能看懂一次智能体请求为什么成功或失败。

当前状态：已完成后台测试弹窗运行摘要和流式事件展示；工作流运行记录已有节点日志详情入口，本阶段不额外扩展小程序。

改动范围：

- 智能体测试弹窗展示运行摘要：
  - `agentCode`
  - `promptId`
  - `workflowCode`
  - `mode`
  - `toolCodes`
- 流式事件展示节点开始、节点结束、来源、错误。
- 工作流运行记录详情中补充工具调用结果展示。

验收标准：

- 测试智能体时能看到工作流节点执行顺序。
- 工具未授权、提示词未启用、工作流未启用等错误能直接显示公开错误文案。
- 工作流运行记录能定位失败节点。

### Phase 4：知识库范围绑定

目标：支持不同智能体使用不同知识范围。

当前状态：已完成后端和后台。采用 `AiAgent.knowledgeTags` 绑定知识标签，复用知识文档 `Document.metadata.tags` 作为范围，不新增知识库集合表；小程序端按本次约定暂不处理。

落地范围：

- 后端 `AiAgent` 增加 `knowledgeTags`。
- 后台智能体表单增加“知识范围”标签配置。
- 普通知识库问答和工作流 `knowledge` 节点按智能体 `knowledgeTags` 过滤 `Document.metadata.tags`。
- 未配置 `knowledgeTags` 时保持全局知识库检索行为。

验收标准：

- 智能体 A 只能检索自己的知识库范围。
- 智能体 B 不会返回智能体 A 独占知识内容。
- 未配置知识库范围时保持当前全局检索行为，避免破坏旧数据。

## 7. 近期推荐落地顺序

建议优先执行：

1. Phase 2：工作流依赖分析和保存校验。
2. Phase 1：智能体欢迎语、推荐问题、分步骤表单。
3. Phase 3：测试链路增强。
4. Phase 4：知识库范围绑定。

原因：

- Phase 2 直接解决当前已经发现的配置矛盾。
- Phase 1 改善配置和聊天入口体验，但不应先于运行正确性。
- Phase 3 提升排查效率，适合在依赖校验之后补。
- Phase 4 涉及数据权限和检索范围，影响面更大，应单独评审。

## 8. 当前不做的内容

为保持当前改动稳妥，以下内容不进入本计划近期实施范围：

- 小程序端智能体配置和展示同步。
- 不把技能包做成独立运行入口；当前运行入口仍为 AiAgent。
- 不新增 MCP 服务管理。
- 不新增子智能体调用。
- 不实现长期记忆和记忆压缩。
- 不引入独立 Studio 执行环境。
- 不重构现有 `knowledge-bot` 对外接口路径。

## 9. 已确认规则

1. 工具字段允许人工收窄额外工具，但不允许移除工作流必需工具；后台会自动合并并锁定必需工具，后端保存时二次校验。
2. 本轮只完成后台和后端，小程序端暂不处理。
