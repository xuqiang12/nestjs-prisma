# AI 运行时能力基础设施开发计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 按“现状契约确认 -> Tool Contract/Catalog 和最小 ToolExecutor -> Workflow Tool 上下文收口 -> Tool Selection -> MCP Tool Adapter -> Workflow Runtime 完善 -> Skill 组合能力 -> Planner 升级”的顺序，稳定新版 Agent Runtime 的能力模型。

**Architecture:** 当前后端已经有 `AgentRuntimeService -> CapabilityResolver -> RulePlanner -> AgentPlanValidator -> AgentCapabilityExecutor -> Handler` 主链路，本计划不重写运行时主流程。第一阶段先建立 Tool 元数据、注册表、最小 Builtin 执行边界和统一结果协议；第二阶段再收口 `ToolHandler` 与 `WorkflowExecutorService` 的上下文传递和工具专属补参。Builtin、REST、MCP 只是 Tool 的不同来源，对 Planner、Validator、Workflow 上层透明。

**Tech Stack:** NestJS、TypeScript、Prisma、OpenAI-compatible LLM SDK、现有 `src/ai-runtime`、现有 contract tests。

---

## 前提假设

1. 本计划只覆盖后端项目 `nestjs-prisma`，不修改 Vue2 后台、小程序或数据库结构，除非后续阶段单独确认。
2. 当前正式 Agent 对话入口是 `POST /agent/chat/stream`，普通 `POST /chat` 不进入 Agent Runtime，不作为本计划第一阶段改造目标。
3. 第一阶段只做 Tool 能力中心收口，不接 MCP 真实客户端，不新增 Skill 大系统，不改成全 LLM Planner。
4. `chat`、`rag`、`tool`、`workflow` 四类能力仍保留；`AgentPlanValidator` 继续作为最终授权边界。
5. `search_knowledge` 定性为内部知识能力或兼容工具，不作为普通业务 Tool 暴露给 Planner 做 Tool Selection。

---

## Runtime 架构铁律

以下规则在所有 Phase 中必须保持；如果某个阶段的实现需要打破任一规则，必须先停止并更新计划，不能边写边补丁。

1. Planner 不执行 Tool。
2. Validator 不执行 Tool。
3. ToolHandler 不直接执行 `ToolDefinition.handler`。
4. WorkflowExecutor 不直接执行 `ToolDefinition.handler`。
5. ToolExecutor 是唯一 Tool 执行入口。
6. Registry 只负责 Tool Catalog，不负责业务执行。
7. ToolDefinition 不承载 Agent 授权状态。
8. Agent 授权由 `AgentContext.capabilities.toolCodes` 和 `AgentPlanValidator` 决定。
9. `search_knowledge` 不作为普通 Agent Tool Selection 对象。
10. MCP / REST / Builtin 对 Planner、Validator、Workflow 上层透明。
11. Skill 不绕过 ToolExecutor。
12. Workflow 不绕过 ToolExecutor。
13. Planner 永远不能绕过 Validator。
14. 不因为未来 MCP / Skill / 多步 Planner 提前实现对应系统。
15. Phase 1 不实现完整权限系统、Adapter Registry、插件市场、连接池或 MCP/REST 真实调用。
16. `ToolDefinition` 永远不包含 `handler`、`execute` 等可执行函数，不承担执行职责。
17. Tool Input 与 `ToolRuntimeContext` 必须分离；Planner 只能填写 Tool Input，不能填写 `userId`、`conversationId`、`signal` 等运行时上下文。
18. `ToolDefinition.code` 是运行时唯一稳定身份，`name` 只用于展示，不能作为授权、持久化或执行查找依据。
19. `exposure = internal` 表示不进入 `PlannerToolCatalog`，不等于 `ToolExecutor` 永久禁止系统内部执行。
20. RAG 不因为 Tool 基础设施建设而强行改造成 `RagHandler -> ToolExecutor -> VectorStore` 调用链。
21. 禁止在 `DefaultToolExecutor` 中按具体 `toolCode` 堆叠业务特判；工具专属逻辑必须留在对应 Builtin/Adapter 实现或业务服务内。
22. `RuntimeToolRegistry` 提供 Catalog API；`DefaultToolExecutor` 不提供 `listTools()` 作为管理侧入口。
23. Phase 1 不引入通用 JSON Schema Validator，`inputSchema` 只作为 Tool Input 契约；LLM 输出校验放到 Phase 3。
24. Workflow 的节点合法性由 Workflow 层负责，Agent 授权由 `AgentPlanValidator` 负责，Tool 系统状态由 `ToolExecutor` 负责。
25. Workflow 不承担 Agent Tool 授权；`ensureToolAllowed()` 若保留，只能校验 Workflow 图内 required tools 与节点声明一致，不能替代 `AgentPlanValidator`。
26. `ToolExecutor` 不生成聊天文本；它只返回机器可读 `ToolResult`，由 `ToolHandler` 转成 AgentEvent/content，由 Workflow 写入 workflow values。
27. Phase 1 到 Phase 6 不实现自动重试、自动 fallback、自动 replan；失败直接形成 `ToolResult` 或 Runtime Error，由当前执行链结束并上报。
28. `ToolDefinition.enabled`、`AgentContext.capabilities.toolCodes`、`PlannerToolCatalog` 是三个不同维度：系统启用状态、Agent 授权清单、Planner 可见目录，不能合并成一个权限中心。
29. `RuntimeToolRegistry.listToolsByCodes(toolCodes)` 只把调用方提供的 code 列表投影成 Tool Catalog 子集，不负责决定这些 code 是否“应该被授权”。
30. Skill 只能提供 `instructions + allowedTools` 等任务上下文，再交给 Planner 产出受控调用；Skill 自己不能变成第二个 Planner 或 Workflow。
31. Phase 1 只建立 Tool 基础设施，不修改 Workflow 调用入口，不升级 Planner，不实现 REST/MCP，不重构 RAG，不提前创建 Skill。

## 最终职责图

这张图是后续所有阶段的压缩版边界。若实现与本图冲突，先停下来更新计划，不要靠局部补丁绕过。

```text
                         AgentRuntimeService
                                  |
                         CapabilityResolver
                                  |
                              Planner
                                  |
                        AgentPlanValidator
                                  |
                     AgentCapabilityExecutor
                                  |
          +-----------------------+----------------------+
          |                       |                      |
          v                       v                      v
     ChatHandler             RagHandler             ToolHandler
          |                       |                      |
          v                       v                      v
     LlmService           KnowledgeQAService       ToolExecutor
                                  |                      |
                           VectorStoreService     +------+------+
                                                  |             |
                                                  v             v

                                                  |             |

                                                                v

WorkflowRuntimeService
          |
```

### 核心架构原则

- Planner 只选择能力和目标，不执行工具，不生成运行时上下文。
- `AgentPlanValidator` 判断 Agent 是否有资格执行该能力、工具或工作流。
- Workflow 层只判断节点在流程内是否合法；流程级 required tools 校验只能证明“工作流声明需要这个工具”，不能证明“当前 Agent 已授权这个工具”。
- `ToolExecutor` 判断工具当前能否被系统执行以及如何执行，包括 `exists`、`enabled`、`source`、Builtin 实现映射和统一错误转换；它不判断 Agent 是否授权。
- `RuntimeToolRegistry` 只提供 Catalog，不执行、不代理管理侧以外的业务逻辑。
- `KnowledgeQAService` 继续作为正式 RAG 核心，不因 Tool Catalog 改造而降级成普通 Tool。
- 失败策略默认是结束当前执行并上报，不自动 retry、fallback 或 replan。
- ToolExecutor 是 Tool 的统一执行基础设施，不是 Agent 授权中心、Planner、Workflow Runtime、RAG Runtime 或用户权限中心。
- 所有普通 Tool 执行最终必须经过 `ToolExecutor.execute(toolCode, input, runtimeContext)`。
- ToolExecutor 不决定 Agent 是否允许使用 Tool，不决定 Planner 选择哪个 Tool，不决定 Workflow 是否应该执行节点，不决定 RAG 是否应该执行，不判断用户是否拥有具体业务权限。

当前结论：

- `ToolHandler` 和 `WorkflowExecutorService` 都已经走 `DefaultToolExecutor`，但 Workflow 仍有工具专属补参和节点级授权逻辑；这是 Phase 2 要治理的架构债。
- `RuntimeToolRegistry` 当前只是 Map 目录，尚未表达 enabled、exposure、source、按已授权 toolCodes 生成可见目录。
- `DefaultToolExecutor` 当前直接执行 `ToolDefinition.handler`，尚未形成 ToolRuntimeContext、ToolResult 和来源隔离。
- `search_knowledge` 当前已在 `CapabilityResolver` 和 `AgentPlanValidator` 中排除为普通工具，但 Tool 定义层还没有 internal 标记。
- Phase 1 不应强行把 RAG 改成 Tool 链路；正式 RAG 仍保持 `RagHandler -> KnowledgeQAService -> VectorStoreService`。
- Phase 1 与 Phase 2 的边界应拆开：Phase 1 建 Tool 协议、Catalog、最小 Builtin 执行；Phase 2 再治理 Workflow/Handler 调用入口和 `buildToolParams()`。

## 执行门禁

每个阶段都必须独立完成、独立汇报、等待确认后再进入下一阶段。

- Phase 0 只读审计，禁止修改源码。
- Phase 1 只建立 Tool Contract、Catalog、最小 Builtin 执行边界和统一结果协议，禁止顺手实现 REST/MCP/权限系统，也不强改 RAG 为 Tool 调用链。
- Phase 2 只收口 Workflow/Handler 工具调用上下文和特殊补参，禁止扩展 Workflow 可视化或节点大改。
- Phase 3 只解决具体 Tool Selection，禁止升级为多步 Planner。
- Phase 4 MCP 只做最小 POC，禁止配置中心、连接池、多租户、持久化。
- Phase 5 Workflow 只做运行时收口，不做前端编辑器。
- Phase 6 Skill 只做组合能力，不保存流程图，不抢 Workflow 职责。
- Phase 7 Planner 升级必须保持 `Planner -> Validator -> Executor` 顺序。

## 总体目标

### 近期目标

把 Tool 从“带 handler 的内置函数列表”收口为一条最小、稳定、可扩展的执行链：

```text
ToolDefinition
  -> RuntimeToolRegistry
  -> BuiltinToolMap
  -> ToolExecutor
  -> ToolResult
```

Phase 1 只负责建立 Tool 的基础设施边界：

- `ToolDefinition` 表达工具元数据。
- `RuntimeToolRegistry` 表达系统中的 Tool Catalog。
- `BuiltinToolMap` 表达 `toolCode -> BuiltinTool` 实现映射。
- `ToolExecutor` 负责统一执行入口和执行错误转换。
- `ToolRuntimeContext` 负责统一运行时上下文。
- `ToolResult` 负责统一机器可读结果。

Phase 1 不治理 Workflow 调用入口，不升级 Planner，不实现 REST/MCP，不重构 RAG。

Agent 授权仍由 `AgentPlanValidator` 负责。Workflow 授权语义在 Phase 2 再收口。Planner Tool Selection 在 Phase 3 再实现。

### 中期目标

在 Tool Catalog、Workflow Tool 调用收口和 Tool Selection 稳定后，把 MCP 作为一种 Tool 来源接入：

- MCP 工具发现结果转换成 `ToolDefinition`。
- Planner 只看到授权后的 `toolCode`、工具描述和参数摘要。
- Validator 仍然校验 Agent 是否授权该工具；工具是否存在、启用、source 是否可执行由 ToolExecutor 处理。
- MCP 第一版只做发现、注册、调用、错误转换的最小 POC。
- MCP 不新增一套独立的 Agent Runtime。

### 长期目标

在 Tool 和 Workflow 稳定后，再补 Skill 和 Planner 升级：

- Skill 作为业务任务说明和工具组合，不保存流程图，不抢 Workflow 的固定流程职责。
- Workflow 继续表达确定性流程，节点可调用 LLM、Tool、Condition，后续再支持 Skill 节点。
- Planner 从只选择 `chat | rag | tool | workflow`，逐步升级到能选择具体 Tool / Skill / Workflow 和受控少步计划。

**设计边界:**

- `ToolDefinition`: 只描述工具元数据和执行来源，不承载上层授权决策，也不包含 `handler/execute`。

- Phase 1 不修改 Workflow 调用入口，不修改 Planner，不修改 CapabilityResolver 的能力选择逻辑，不修改 RAG。

**ToolDefinition 建议字段:**

```ts
export type ToolSource = 'builtin' | 'rest' | 'mcp'

export type ToolExposure = 'internal' | 'agent'

export interface ToolDefinition {
  code: string
  name: string
  description: string
  source: ToolSource
  exposure: ToolExposure
  enabled: boolean
  inputSchema: JsonSchemaObject
}
```

字段语义必须固定：

- `code`: 运行时唯一稳定身份，用于注册表查询、Agent 授权、持久化配置和执行调用。
- `name`: 展示名称，可改文案，不能作为执行或授权依据。
- `source`: 工具来源，Phase 1 只对 `builtin` 有真实执行实现。
- `exposure`: 工具是否能进入 Planner 可见目录；`internal` 不进入 `PlannerToolCatalog`。
- `enabled`: 系统级启停状态；Agent 已保存的 `toolCodes` 可以保留，但执行和 Planner 可见目录必须过滤禁用工具。
- `inputSchema`: JSON Schema-compatible object，只描述用户或 Planner 需要提供的业务输入，不包含 `userId`、`agentCode`、`conversationId`、`signal` 等运行时上下文字段。

`JsonSchemaObject` 在 Phase 1 只需要表达最小 JSON Schema 对象契约，可放在 `tool.types.ts` 中：

```ts
export type JsonSchemaObject = {
  type: 'object'
  properties?: Record<string, JsonSchemaProperty>
  required?: string[]
  additionalProperties?: boolean
}

export type JsonSchemaProperty = {
  type: 'string' | 'number' | 'integer' | 'boolean' | 'array' | 'object'
  description?: string
  enum?: unknown[]
  items?: JsonSchemaProperty
  properties?: Record<string, JsonSchemaProperty>
  required?: string[]
  additionalProperties?: boolean
}
```

Phase 1 只定义 Schema 契约，不做运行时校验；Phase 3 的 Planner Tool Input 再引入校验或规整。

**ToolRuntimeContext 建议字段:**

```ts
export interface ToolRuntimeContext {
  userId: string
  agentCode?: string
  conversationId?: string
  requestId?: string
  traceId?: string
  signal?: AbortSignal
}
```

Tool Input 与 RuntimeContext 的边界：

- Tool Input 来自用户、Planner、Workflow 节点配置或 MCP 调用参数。
- RuntimeContext 来自 Agent Runtime / Workflow Runtime 自动注入。
- Planner 只能看到并填写 Tool Input；Planner 不应该知道 `userId`、`conversationId`、`requestId`、`signal` 等字段。
- `get_user_menu_permissions` 需要的 `userId` 应在 Builtin Tool 执行实现中从 `ToolRuntimeContext.userId` 获取，而不是由 Planner 或 Workflow 节点参数提供。

**ToolResult 建议字段:**

```ts
export type ToolErrorCode =
  | 'TOOL_NOT_FOUND'
  | 'TOOL_DISABLED'
  | 'TOOL_SOURCE_UNSUPPORTED'
  | 'TOOL_IMPLEMENTATION_NOT_FOUND'
  | 'TOOL_EXECUTION_FAILED'

export type ToolResult<T = unknown> =
  | {
      success: true
      data: T
    }
  | {
      success: false
      error: {
        code: ToolErrorCode
        message: string
      }
  }
```

ToolResult 第一版保持克制，只固定错误码，不提前加入 `latency/source/metadata/rawResponse/retryable/httpStatus/mcpSession` 等未来字段。

ToolResult 消费边界：

- `ToolExecutor` 只产出 `ToolResult`，不负责把结果改写成人类聊天文本。
- `ToolHandler` 负责把 `ToolResult` 转成 `tool_done`、`content`、`error` 等 AgentEvent。
- `WorkflowExecutorService` 负责把 `ToolResult.data` 写入 workflow values 或把 `ToolResult.error` 转成工作流错误事件。
- Tool 专属展示文案只能放在 Handler/Presenter 层，不进入 `ToolExecutor`。

Phase 1 固定错误码：

- `TOOL_NOT_FOUND`: Registry 找不到该 `toolCode`。
- `TOOL_DISABLED`: 工具存在但 `enabled = false`。
- `TOOL_SOURCE_UNSUPPORTED`: `source = rest | mcp` 但当前 Phase 尚未实现真实执行。
- `TOOL_IMPLEMENTATION_NOT_FOUND`: `source = builtin` 但 Builtin 实现映射里找不到对应 `code`。
- `TOOL_EXECUTION_FAILED`: Builtin 实现执行时抛错或返回不可消费结果。

**权限边界:**

- Agent 授权：`AgentContext.capabilities.toolCodes` 表示该 Agent 允许使用哪些工具。
- Tool 状态：`ToolDefinition.enabled` 和 `ToolDefinition.exposure` 表示工具是否可进入运行时和是否可被 Agent 选择。
- Planner 可见目录：上层通过 `RuntimeToolRegistry.listToolsByCodes(agent.toolCodes)` 取回工具子集后，再过滤 `enabled + exposure` 形成 `PlannerToolCatalog`；它只决定模型能看见什么，不替代 `AgentPlanValidator`。
- 用户业务权限：由 Tool 内部或业务服务判断，`ToolExecutor` 不变成超级权限中心。
- Phase 1 不在 `ToolDefinition` 中加入 `requiredPermissions`；等真实工具权限需求出现后再单独设计。
- `search_knowledge` 若继续注册，必须是 `exposure = internal`，不能被普通 Tool Selection 选中。
- `internal` 不等于绝对不可执行；如果未来 RAG 内部要通过 ToolExecutor 调用 internal 工具，必须另起设计确认，不能在 Phase 1 顺手改造。
- `Agent.toolCodes` 只能保存 `enabled = true && exposure = agent` 的工具 code；`search_knowledge` 等 internal 工具不能被保存为普通 Agent 工具授权。
- 已保存但后来禁用的工具 code 可以保留为历史配置，但运行时和 Planner 可见目录必须过滤，管理侧应提示不可用而不是静默执行。

### Agent.toolCodes 校验

`AgentService` 只负责校验：

1. `toolCode` 是否存在。
2. Tool 是否允许作为 Agent Tool。
3. Tool 是否 `enabled`。
4. Tool `exposure` 是否为 `agent`。

`AgentService` 不负责判断当前请求是否有权执行 Tool。

运行时执行授权仍由：

```text
AgentContext.capabilities.toolCodes
  -> AgentPlanValidator
```

完成。

`AgentService` 不新增 `ToolAuthorizationService`。

**工具状态决策表:**

| 状态 | Planner 可见 | Agent 可配置 | ToolExecutor 可执行 |
| --- | --- | --- | --- |
| `enabled = true`、`exposure = agent`、Agent 已授权 | 是 | 是 | 系统层可执行；Agent 授权已由 Validator 前置确认 |
| `enabled = true`、`exposure = agent`、Agent 未授权 | 否 | 是 | ToolExecutor 不判断；应由 `AgentPlanValidator` 拒绝进入执行 |
| `enabled = true`、`exposure = internal` | 否 | 否 | 视内部调用链单独确认，Phase 1 不开放给普通 Agent |
| `enabled = false`、`exposure = agent` | 否 | 建议保留历史配置但禁止新增选择 | 否 |
| `enabled = false`、`exposure = internal` | 否 | 否 | 否 |

**统一命名:**

- 对外执行方法统一使用 `execute(toolCode: string, input: unknown, context: ToolRuntimeContext): Promise<ToolResult>`。

**REST/MCP 硬边界:**

**ToolExecutor 严格禁止:**

- Agent 授权。
- 用户业务权限。
- Planner 决策。

- Workflow 参数转换。

- Tool Selection。
- Retry。
- Fallback。
- Replan。
- 具体 Tool 业务逻辑。

ToolExecutor 只执行：

1. 根据 `toolCode` 查询 `ToolDefinition`。
2. 判断 Tool 是否存在。
3. 判断 Tool 是否 `enabled`。
4. 判断 Tool `source` 是否支持。
5. 根据 `source = builtin` 从 `BuiltinToolMap` 获取实现。
6. 调用 `BuiltinTool.execute(input, runtimeContext)`。
7. 将异常统一转换成 `ToolResult`。

最小关系固定为：

```text

  -> ToolDefinition[]

ToolHandler / Phase 2 WorkflowExecutor
  -> DefaultToolExecutor.execute(toolCode, input, runtimeContext)
  -> RuntimeToolRegistry.getTool(toolCode)
  -> BuiltinToolMap.get(toolCode)
  -> BuiltinTool.execute(input, runtimeContext)
  -> ToolResult
```

- [ ] `RuntimeToolRegistry` 不包含执行方法或 handler 调用。
- [ ] 管理侧工具列表不通过 `DefaultToolExecutor.listTools()`。

### Phase 6: Skill 概念验证与最小组合能力

**目标:** 在 Tool、Workflow、Planner 都稳定后，判断 Skill 是否确实需要作为独立运行时能力存在。

**拟新增文件:**

- Create: `src/ai-runtime/skill/skill.types.ts`
- Create: `src/ai-runtime/skill/skill-registry.service.ts`

**Phase 6 开始前必须先回答:**

1. Skill 与 Workflow 的边界是什么。
2. Skill 与 Tool 的边界是什么。
3. Skill 是否需要独立持久化。
4. Skill 是否需要作为 `CapabilityType`。
5. Skill 是否只是 Planner 上下文，而不是独立执行对象。

第一版如果确认 Skill 存在，Skill 只负责：

- `instructions`
- `inputSchema`
- `allowedTools`

**设计边界:**

- Skill 是业务任务说明和工具组合，不是第二套 Workflow，不是第二套 Agent Runtime。
- Skill 不保存流程图；Workflow 保存确定性流程图。
- Skill 可以声明 `instructions + allowedTools`，但不能自己决定多步执行顺序。
- Skill 不直接调 ToolExecutor；推荐方向是 Skill 提供任务说明和工具范围，由 Planner 生成受控 Tool 调用计划，再经过 `AgentPlanValidator` 和 `CapabilityExecutor`。

- Skill 是否纳入 `CapabilityType = 'skill'` 需要在本阶段开始前单独确认。
- 第一版只做后端运行时，不做前端编排器。

**验收标准:**

- [ ] Skill 能声明自己需要哪些 Tool。
- [ ] Agent 只能使用被授权的 Skill。
- [ ] Skill 不直接执行工具，而是进入 Planner -> Validator -> Executor 链路。
- [ ] Skill 不绕过 `AgentPlanValidator`。
- [ ] 未确认 Skill 边界前，不创建 `SkillExecutor`。
